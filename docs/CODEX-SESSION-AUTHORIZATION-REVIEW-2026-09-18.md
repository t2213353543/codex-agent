# 已绑定会话分组授权复核

本轮仅本地合成账户和 loopback 上游，无真实账号、公网推理或部署。独立复核只新增 `gateway_session_authorization_test.go`；生产修复由主任务负责。

## 修复前证据

普通密钥只允许 `group-one`，账户最初也在该组。完成首轮并建立固定账户绑定后，通过 Store 把账户移到 `group-two`，不调用调度缓存失效；测试明确检查缓存仍在 5 秒窗口内，保留旧分组和启用状态。

- HTTP 单项先失败：`status=200 upstream_requests=2`，0.044 秒。
- HTTP/WS 合并复现失败：HTTP 同上；WS 第二轮返回 `response.completed`，`upstream_turns=2`，0.150 秒。
- 两端禁用账户、撤销密钥组、未变更三个对照原本均通过。

另有同组可用替代账户，测试检查旧绑定没有迁移，也没有占用替代账户的并发名额。问题是缓存分组允许了未经当前账户组授权的后续请求，不是账户身份改变。

## 修复后验证

主任务在绑定账户重新读取之后、HTTP `ensureReady` 返回之后，以及 WS 每轮的当前账户授权路径调用当前分组检查。普通密钥要求账户组与当前密钥组有交集；管理员仍保留跨组权限，取消上下文被拒绝。

三个顶层测试、13 个子场景连续运行 3 次通过，0.681 秒：

```powershell
go test ./... -run '^TestGatewaySessionAuthorization' -count=3 -timeout=90s
```

覆盖 HTTP/WS 移组拒绝、禁用、密钥组撤销、未变更、仍有组交集，以及管理员跨组、取消上下文和刷新后返回账户的分组检查契约。后者直接测试 helper 输入，不伪造 OAuth 服务能修改管理分组。

恢复原组后，HTTP 使用原 session 继续；WS 授权失败会按已有行为关闭连接，恢复后重新连接同一 session，原账户绑定仍可继续。不宣称被拒的原 socket 可以复用。
