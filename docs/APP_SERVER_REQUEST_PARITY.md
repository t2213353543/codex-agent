# App Server 0.155.0 request parity

This is an evidence ledger, not a claim that the existing `official_codex_cli` mode is equivalent to App Server. The reference is the repository's fixed `.local/codex-source-0.155.0` tree plus actual executable captures. Source behavior and captured behavior are tracked separately. No model catalog entries, credentials, hidden routing headers or quality improvements are fabricated.

## Boundaries

`official_app_server` rebuilds a thread through `thread/start`, `thread/inject_items` and `turn/start` (`internal/server/gateway_official_responses.go:273`, `:434`, `:438`). The project's `official_codex_cli` Responses route instead applies policy, prepares JSON/cache keys, and forwards through the native transport (`internal/server/gateway.go:539`, `:671`, `:688`, `:742`, `:747`). The two routes selecting `codexURL` does not imply matching requests.

The lightweight writer must leave tool execution and full conversation ownership with the client. It must not spawn a hosted agent or manufacture hidden conversation state. The pure `buildAppServerRequest` boundary accepts immutable actual model metadata, caller-owned model context, serialized tool definitions and explicit identity snapshots. It generates the official writer's body and HTTP headers. Context assembly and incoming Responses compatibility are separate adapters, validated against capture before handler integration.

This proves the final writer/envelope boundary for this pilot, not connection reuse, tool execution, other models or all App Server operations.

Safe fixtures: `internal/server/testdata/appserver_writer_pilot.json`; exporter: `tools/appserver_parity_writer_fixtures.py`. Raw captures and authentication stay on the private server. The first comparison exposed a Go header-map casing issue: JSON-loaded lowercase extra header keys were invisible to `Header.Get`. The writer now canonicalizes supplied keys with `Header.Add`.

The actual model entry selected Lite, default effort `medium`, summary `none`, verbosity `low`, and `tool_mode=code_mode_only` before the bridge changed tool mode. The client sent no tools, but the runtime exposed `functions` (request_user_input_async/apply_patch/goal tools), `clock` and `collaboration` namespaces. These are retained in the fixture. Removing them or exposing them to a client unable to execute them is a separate semantic decision, not writer parity.

The initial generation added permission/collaboration, multi-agent role, multi-agent mode and environment context before the synthetic user message. `buildAppServerInitialContext` now reconstructs the captured read-only/never/single-environment profile from actual catalog message fields plus pinned Rust-source fallbacks. `TestAppServerContextMatchesExecutableCapture` compares all four generated messages against the independent executable capture, including content order/classifications, with explicit captured IDs/timestamps supplied by the caller. It also verifies retained context is not reinjected. This adapter returns additions and never rewrites caller history. Other sandbox/approval/environment profiles remain to be validated.

Pinned fallback assets are generated by `tools/appserver_source_templates.py`; the embedded JSON contains source paths and SHA256 values. Catalog-provided empty values suppress fallback. No live model catalog is embedded as application behavior.

The lightweight gateway retains instruction-field provenance across generic HTTP preparation. When the original post-policy body omitted `instructions`, the compatibility layer's inserted empty string is removed before the catalog-backed writer. A caller's explicit empty string and a configured policy prompt remain authoritative. A full gateway integration test verifies all three origins plus an explicit nonempty caller instruction. Native already-built Lite and response-delta bypasses remain unchanged.

## Verification rules

1. Capture every actual executable outbound HTTP operation and WS message, including bootstrap and retries. Use loopback placeholder credentials for deterministic fixtures.
2. Compare model-visible input ordering, instruction bytes, tools/schema, controls, null/omission behavior, and header projections. Dynamic identities may be consistently renamed for comparison; do not remove semantic fields.
3. Reproduce first turn, tool-result continuation, user second turn, model switch, structured output, compaction, reconnect/fallback and failure. Successful HTTP alone is not semantic parity.
4. Attach actual capture provenance to fixtures. Source-derived unit cases are not labeled as captured evidence.
5. Production use is opt-in via CODEX_APP_SERVER_CLI=1. Writer, tool and HTTP-boundary tests do not establish perfect hosted-runtime equivalence; consult APP_SERVER_CLI.md for actual live results and remaining profile differences.

Local pure and captured checks: `go test ./internal/server -run '^TestAppServer(Context|Request)' -count=1`.
