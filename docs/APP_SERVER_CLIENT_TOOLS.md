# Client-owned App Server tool profile

`buildAppServerTools(raw, lite)` returns an immutable `appServerToolAdapter` with ordered `Tools` JSON plus `PrepareInput`, `MapOutputItem`, `MapEvent` and `PrepareToolChoice` methods. It performs no execution, discovery, persistence, alias hashing or conversation management. Only client declarations are exposed.

The source reference is Codex 0.155.0 `tools/src/tool_spec.rs:95` (Lite grouping), `tools/src/responses_api.rs:17` (custom/function/namespace field order), and `protocol/src/models.rs:1061` (native function/custom call and output shapes). Ordinary function/custom tools join the `functions` namespace at the position of the first default tool. Other namespaces and built-ins retain their order. A nonempty explicitly supplied `functions` namespace description wins, matching the Rust grouping routine. Duplicate effective identities fail instead of silently selecting one.

Legal names remain unchanged. A Lite return with `namespace: functions` is mapped back to the caller's original default scope; explicitly namespaced declarations retain their scope. Client history restores the needed default namespace. Call IDs, server item IDs, grammar input text, function argument strings, structured tool outputs, opaque encrypted reasoning and retired-tool history remain intact. Partial SSE/WS argument and custom-input deltas pass through without parsing their partial text. Item events and terminal response output arrays share the same mapping.

Custom grammar tools remain native `custom` ToolSpecs and `custom_tool_call`/`custom_tool_call_output` items. They are not converted into JSON-argument function wrappers. The captured native grammar schema accepts `format.type=grammar` with `lark` or `regex` syntax. Function `strict`, schema bytes, unknown schema extensions and large integers remain client-owned. This intentionally differs from the hosted DynamicTool RPC path, which only accepts functions and calls `parse_tool_input_schema` to sanitize, prune and potentially compact schemas. The adapter does not claim byte parity with that registration pipeline for arbitrary client schemas.

`web_search` stays a real backend tool and preserves explicit false flags and empty `search_content_types`; `web_search_preview` is normalized to that supported ToolSpec name. A returned `web_search_call` passes through. The mapper does not invent a client `web/run` function, invoke the runtime's `alpha/search` endpoint, or claim those two mechanisms are equivalent. `tool_search` remains its own ToolSpec and retains the requested execution mode.

The lightweight request adapter now explicitly selects `StandardTools` for an incoming top-level `web_search`/`web_search_preview`. This follows the same-account capture result: standard HTTP produced an actual `web_search_call` and citation, whereas Lite `additional_tools` did not execute search. The actual catalog entry remains immutable. The chosen wire profile places instructions/tools at the top level, omits Lite-generated prefixes/header/default `reasoning.context`, and preserves any explicit caller reasoning context. Function/custom declarations alongside search remain available without Lite namespace grouping. The request dispatches directly once through native HTTP and its normal compression/account boundary, without WebSocket prewarm or any server search/agent loop. Already-constructed Lite input still passes through unchanged.

`PrepareToolChoice` preserves explicit `auto`, `none`, `required` and selected tool choices. It never adds a namespace to a selected top-level tool: the real Lite upstream rejected the formerly added `tool_choice.namespace` with `invalid_request_error` / `unknown_parameter`. An explicitly supplied namespace remains caller-owned and may produce that real upstream rejection; support is not claimed. Preserving forced choices is an explicit client-contract override because the official 0.155.0 agent writer always sets `tool_choice: auto`.
