# 首次账户选择的当前状态校验

本轮承接已绑定会话的授权修复，补齐尚未绑定请求的账户选择边界。所有验证均为本地合成数据，不使用真实账号、不部署；Rust helper 未修改。

## 已复现问题

`pickAccount` 原先从五秒调度缓存选中账户，未过期令牌直接通过 `ensureReady`，因此可能继续使用已停用、移出 key 授权分组或已删除的账户。并发上限从 100 降为 1 时，也可能按缓存的 100 再准入。

修复前实际观察到：上述三种撤销在新会话、无会话两种入口均把请求发送给旧账户；唯一候选已撤销时仍发送并错误建立绑定；当前并发限额为 1 且已有请求时再次准入，active 达到 2。

## 实现

- 保留候选发现与优先级/权重的调度快照，但抽中候选后按稳定 ID 重新读取当前账户，随后检查当前启用状态、账户组与本实例当前 key 组的交集，再进行冷却及并发准入。
- 使用读取到的当前凭据、Concurrency 和代理列表。新请求尚未绑定，可选择该管理记录当前合法 owner；既有 binding 仍保持原来的严格 owner 校验，不因此被迁移。
- 账户已删除、停用或不再属于允许组时仅跳过该候选。它们不记作 OAuth 故障，也不让“剩余合法账户都忙”的 429 变成 503。全部无可用候选时仍拒绝，不发送或建立绑定。
- 当前账户读取异常、请求取消、key 失效或 ID 不符会终止选择，不使用缓存兜底。刷新成功后再次校验授权，已轮换 AT/RT 照常保存；撤权后不发送模型请求、不写入伪 OAuth 错误。
- 新增 `pgGetContext` 复用原来的只读 RepeatableRead 事务，将新选择读取的 context 传入数据库连接获取与查询；旧 `pgGet` 调用仍保留 Background + 15 秒上限。请求取消在新读取后优先返回，刷新阶段的取消也在记录账户错误前结束选择。

没有持调度缓存锁或准入锁等待数据库/刷新。每个实际尝试的候选增加一次当前账户读取，这是正确性与数据库开销的明确取舍；未据此宣称生产延迟改善。

## 覆盖

JSON 文件/HTTP 回归包含撤销候选后选择合法备用、全部撤销无派发/无绑定、当前并发限制、合法账户忙时的 429、当前 AT 与新 owner、已有绑定仍拒绝旧身份、损坏存储不回退缓存、预取消，以及刷新期间禁用 key/移除允许组但仍保存新凭据。

PG/Redis 回归使用独立 writer/reader，初始同步 key 索引后仅修改账户：撤组/停用/删除各有无备用、当前并发限制、凭据及 owner 更新。另用独立单连接池占满连接，并由 pgx AcquireTracer 确认新账户读取已等待，再取消请求，检查及时返回 `context.Canceled`、无准入、无 HTTP 调用、原账户错误及凭据版本不变。

## 明确边界

候选发现和排序仍有原五秒缓存：新近启用/授权而尚未出现在候选集中的账户可能等待缓存更新。普通 key 的读取仍是本实例索引，不宣称跨实例 key 撤权即时广播。初始列表读取、既有刷新路径和文件系统 I/O 不因新增 `pgGetContext` 就全部变成可取消。

这是多个检查点，不是管理更新、令牌刷新和网络发送的原子事务。`ensureReady` 原有静态 owner 检查没有扩展为覆盖所有未知身份或 OwnerRevision ABA 变化。当前读取异常的失败关闭也不代表本轮重写了所有刷新内部数据库错误分类。
