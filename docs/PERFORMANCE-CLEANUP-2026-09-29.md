# 精确清理任务的扫描优化

`POST /api/logs/cleanup/preview` 保留固定可见 ID 的契约：同一条 `INSERT ... SELECT` 捕获事务可见的成员，之后提交的低序号记录不会被加入。创建任务仍将该成员集延长至任务完成，清理仅删除请求明细，不删除永久用量事件。

本次移除了两处重复遍历：

- 预览直接使用插入命令的 `RowsAffected()` 取得精确数量，最高 ID 通过 `(preview_id,log_id)` 主键倒序 `LIMIT 1` 取得；不再对刚写入的全部成员再执行 `count(*)`。
- 每批最多清理 1000 个成员后，用本批实际清除的目标数量更新 `Remaining`，替代对全部剩余成员的 `count(*)`。对 N 个目标，原来需要扫描大约 `N + (N-1000) + (N-2000) + ...` 行，本次将进度维护降为每批固定工作量。

`Deleted` 与 `Remaining` 使用不同的计数。其他清理任务或明细保留策略可能提前删除记录，但不会删除本任务的成员行，因此本批清除了 1000 个成员、只删到 0 条明细时，剩余工作仍应减少 1000。成员清除、实际删除、进度和完成审计在同一事务内提交；同一任务继续由原有数据库锁串行执行。

初始化剩余数量使用创建任务时保留的实际成员数。对于已经不一致、剩余数小于本批目标数的旧检查点，保留一次完整重新计数；正常执行不走该分支。数据量越大，避免每批重新计数的收益越明显。构造成员集本身仍需写入全部选中 ID，不能据此宣称千万成员的预览已低于 3 秒。

验证包括原有清理生命周期、低 ID 延后提交、取消、审计失败回滚，以及新增的 2505 个重叠目标、同任务两个进程并发恢复、永久用量保留和最终审计次数。真实 PostgreSQL 三项功能测试已全部通过，无跳过：`.local/performance-slo/20260929t012552-c537d6/report.json`，源码 `bb3e47e15da22f59ec955025ff57744f74272efa24e18c6a9bf2839dea35d0b5`。这份报告验证语义，不宣称大规模预览的正式 SLO。
