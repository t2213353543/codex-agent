第二阶段已验证基础读取，但复杂筛选仍有遗漏。第三阶段先对同一个真实千万行合成库执行原版请求，保留超标/失败证据，不把基础查询的通过推广到全部参数组合。

## 筛选索引

014 定义不可变的 `request_log_filter_tags` 紧凑 JSON 投影，015 以 `jsonb_path_ops` 建 GIN 索引。它只包含管理筛选字段及 groups，不把大型错误/协议正文复制进索引。一个索引可覆盖多个等值条件的 AND；长字符串经 GIN 路径 hash 再由 PostgreSQL recheck，不会遇到 BTree 文本项长度限制。

应用保留原有 WHERE 条件，并加投影 containment 作为访问路径。投影字段遵循现有 `->>` 文本表示、boolean cast、stream 默认 false、可选布尔 missing 不等于 false 等语义。groups 保持 PostgreSQL `?` 的匹配含义，包括历史字符串或对象键形式；合法 request record 的常规形式为去重意义上的数组成员。

单独新增 input/output/cached token 排序复合索引，和原 `(value,created_at,id)` seek 顺序一致。模型排序将短文本与超长合法文本分开取有界排序页后合并，短文本使用 BTree，长文本保留独立部分索引；不会为性能拒绝既有合法长模型名。

普通模型排序仍使用兼容 v1 文本游标；序列化后超过 1 KiB 时改为 v2 边界引用（保留记录 ID、时间、模型 SHA256），下一页按主键校验并取得完整模型与实际索引时间戳。这样 50,000 字节文本和 HTML 转义放大的模型也不会生成超限 URL。边界已被清理或模型发生变化时明确要求重新分页，不悄悄使用不同排序边界。其它排序不再嵌入无用模型文本。旧 v1 模型游标接受 64 KiB 作为兼容预算，新生成游标始终有界。

## 状态与排序相关性

实际 error + model + tokens 查询使用旧 token 排序索引时，先跳过约 225,000 条成功记录才取得一页。新增 016 以 status 为前导键，让失败请求的最高 token 排序直接定位其有序范围。

只有新索引仍不够：预备语句通用计划对未知 LIMIT 参数估计过宽，选择大位图和排序，仍超 15 秒。页面 SQL 现在将经过 size≤500/page≤100 校验的分页整数作为 SQL 数字常量，其余所有用户筛选值继续绑定。通用计划能按一页实际数量评估索引停止位置，不需要修改全局 planner 设置。

`.local/performance-slo/20260929t003716-52b6fb/report.json` 使用真实查询和 `EXPLAIN EXECUTE` 验证：定制计划约 4.117 ms，强制通用计划约 2.475 ms，均使用 `request_logs_status_tokens_time_idx` 取得一页。此前诊断在 query timeout 后连接被重建时，session SET 可能丢失，故新工具把 plan_cache_mode 写入连接运行参数，并直接解释预备语句，避免把另一个临时计划冒充缓存计划。

这些结构诊断与 uniform 造数并行，只证明访问路径及语义，不作为排他环境的正式尾延迟验收。

## 验证与维护

`.local/performance-slo/20260929t001158-045cf0/report.json`：typed filter SQL 与 file 匹配逐行等价、默认/缺失布尔、历史 groups 表达形式、数千字节模型升降序/游标/页码、原始查询导出合同全部通过；强制 custom/generic 对精确筛选和各排序断言指定索引且没有全表扫描。

013 身份不一致守卫、015/016 索引通过原在线迁移机制逐项 claim/checksum/真实定义检查和中断恢复。第一次大表构建的最后阶段因旧批量事务快照超过 30 秒而返回 55P03，已将仅维护连接的 lock_timeout 调整为 2 分钟，仍在结束后恢复原连接值。已成功构建的索引不重做，续跑约 10.761 秒完成未完成部分。016 单独实际维护约 29.468 秒。

正式性能复测将等待均匀千万级造数结束、无并行维护后运行；当前源码/语义和执行路径证据不替代该最终阶段。新增索引增加磁盘和写入工作量，最终报告应同时记录体积与持久入库延迟。
