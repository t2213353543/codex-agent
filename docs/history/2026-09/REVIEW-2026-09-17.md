# Codex Agent 完善建议 · 2026-09-17

本次检查范围为管理后台、账号管理、代理管理、日志统计、存储与部署。按 PostgreSQL + Redis 作为目标架构提出建议，不涉及 Codex 网关的调度、转发、计费、限流或路由实现。本次未修改业务源码、线上配置或生产数据。

当前事实：本地与线上二进制 SHA256 一致；线上进程仍通过 `--data /var/lib/codex-agent` 使用 JSON/JSONL 文件。`main.go:61` 初始化的是文件 Store，`go.mod` 没有数据库驱动。因此，以下 SQL 是迁移设计建议，不是已经测出的慢 SQL。线上日志在检查时为 0 字节，不能据此推断大数据性能。

## 2. UI、布局与样式

保留 Vue 3 + Element Plus 和现有中性色主题体系，优先改信息密度和操作路径。

- **账号页主次分明。** 默认仅保留账号名、凭据状态、过期时间、所属标签/分组、代理摘要与操作；低频信息放详情抽屉。名称列和操作列固定，错误用简短摘要，点击查看完整内容。账号量增大后使用服务端搜索、排序、分页。
- **补齐响应式布局。** 手机侧栏改抽屉，顶栏只保留必要操作，主题和用户菜单收进下拉；登录卡、对话框使用视口约束。筛选区窄屏折叠，表格局部横滚而不是撑破整个页面。长错误、长账号名应可折行。
- **统一设计变量。** 统一间距、圆角、输入框高度、表格行高和正文/辅助字色，逐步去掉页面内联尺寸；浅色、深色、海蓝、翡翠共享语义变量。状态同时带文字和图标，不只依赖红绿颜色。
- **仪表盘降低重复。** 顶部横条和 KPI 卡有重复指标，减少一组；明确“今日”“所选范围”“累计”的统计口径。错误项直接打开相应日志或账号，图表无数据时显示解释而不是空白画布。
- **页签保持筛选状态。** 当前多页签仅记录路由，页面切换后筛选与滚动会重置；用 URL query 或独立页面状态保存。刷新用组件刷新事件，不把 `/redirect` 存入 visitedTabs。限制未知/失效页签。
- **移除失真的 UI 信息。** 通知铃铛目前常亮红点却没有行为，应接真实到期/检查失败通知或暂时隐藏；侧栏写死 v2.1.0，而后端为 0.2.0，应使用后端版本与构建 ID。
- **操作反馈一致。** 提交时防重复，删除提示受影响账号数；错误显示原因和恢复入口，不能 catch 后静默。Clipboard 不可用时提供可选中文本框，不在 toast 直接展开完整管理密钥。
- **键盘可用。** 折叠、主题、刷新、关闭页签按钮有 aria-label 和可见 focus；弹窗焦点返回触发按钮。确认删除和取消分别测试。

## 3. 值得增加的管理功能

按实际使用价值排序，不扩展网关能力：

1. **账号详情抽屉**：备注、标签、创建/更新时间、凭据到期、最近一次验证与失败原因、绑定代理；敏感令牌默认不返回前端。
2. **批量操作与导入预览**：批量启停、设置标签/备注、绑定或解绑代理；导入逐行结果、重复处理、失败项下载；保留幂等任务 ID，避免重复点击产生重复记录。
3. **凭据维护**：手动验证、手动刷新、刷新进度、到期提醒；区分“令牌未过期”和“已实测可用”。对同一账号只允许一个凭据刷新操作。
4. **代理诊断历史**：显示上次检测结果、出口 IP、延迟和失败环节；编辑密码时空白表示保持原值，列表只返回 has_password。
5. **管理审计**：记录账号导入、编辑、删除、凭据更新、代理修改和设置变更；记录操作者/会话与结果，不记录令牌正文。
6. **筛选和导出**：保存常用筛选，按名称/状态/到期时间查询；默认导出账号元数据与脱敏日志，不把凭据混进常规 CSV。
7. **运行诊断**：版本、启动时间、PG/Redis 可用性、最后一次成功写入/聚合时间、最近后台任务失败。健康检查分 liveness 与 readiness。

## 4. PostgreSQL + Redis 的边界

| 组件 | 建议保存的数据 | 约束 |
|---|---|---|
| PostgreSQL | 账号元数据、加密凭据、分组/标签关系、代理配置、操作审计、日志、聚合、设置 | 唯一持久事实来源；事务、外键、唯一约束、版本号控制一致性 |
| Redis | 短期管理会话、少量热点概览缓存、短期任务状态、非关键提示 | 缓存全部可由 PG 重建；短 TTL；账号修改后失效；不作为凭据或统计的唯一存储 |

建议从这些表开始，按需求裁剪：

| 表 | 关键设计 |
|---|---|
| accounts | 内部 id、display_name、enabled、备注、凭据状态、last_checked_at、created_at/updated_at、version；名称不作为外键 |
| account_credentials | account_id 唯一、加密 AT/RT、expires_at、credential_version、encryption_key_id；与普通列表查询分离 |
| groups / account_groups | 复合主键 `(account_id, group_id)`，两个外键，反向查询索引 `(group_id, account_id)` |
| proxies / account_proxies | 代理元数据与加密密码；关联表复合主键，按代理 ID 的反向索引 |
| request_logs | 内部 id、event_id、account_id、created_at、status、model、耗时、token 数、脱敏错误；保留名称快照 |
| usage_minute / usage_daily | 时间桶与账号 ID 的唯一组合；由日志事件幂等汇总，可以重建 |
| audit_logs / settings | 操作审计追加写；设置值可用 JSONB，但查询、排序、关联字段应为显式列 |

凭据在应用层加密，密钥由部署环境单独提供。稳定身份去重需要核实上游用户 ID 与工作区 ID 的组合语义；不对尚未确认的 `account_id` 直接加全局唯一约束。删除账号时保留历史日志，可采用逻辑删除或可空外键加名称快照。

账号编辑使用 `version` 做乐观并发控制，冲突返回 409 和最新数据，避免两个浏览器页面互相覆盖。关系修改在同一事务内完成；外键负责防止悬空关系。见 [PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)。

刷新令牌的并发控制应按账号划分。当前全文件锁覆盖最长 45 秒网络交换，而其他账号写操作仅等 2 秒，容易连带阻塞。迁移后可以用专用连接上的账号级 advisory lock 串行化刷新，短事务保存新凭据并校验版本；必须显式释放锁，不能把持锁连接随意归还池，也不要跨 OAuth 网络请求持有普通行事务。见 [PostgreSQL 锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)。

若采用 Redis 租约，则需要唯一持有者值、TTL、续期、条件释放和 PG 版本校验；不能以简单 SETNX + DEL 代替完整刷新一致性。租约过期时仍在进行的外部刷新需要明确失败处理。见 [Redis 官方锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

## 5. SQL 与性能优化

以下为设计示例，未在生产执行，也不代表已测得索引收益。

**日志优先采用稳定游标分页。** 普通列表和单账号日志先各有一个索引，之后根据查询统计决定是否新增错误筛选索引。

```sql
CREATE INDEX request_logs_time_idx
    ON request_logs (created_at DESC, id DESC);

CREATE INDEX request_logs_account_time_idx
    ON request_logs (account_id, created_at DESC, id DESC);

-- 后续页示例；首屏用不带游标条件的独立查询。
SELECT id, account_id, created_at, status, model, latency_ms, error_code
FROM request_logs
WHERE account_id = $1
  AND (created_at, id) < ($2::timestamptz, $3::bigint)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

复合 B-tree 索引应匹配等值筛选与时间排序，不给每列或每个组合都加索引。见 [PostgreSQL 多列索引文档](https://www.postgresql.org/docs/current/indexes-multicolumn.html)。

- **消除 N+1。** 当前账号列表对每个账号再次读取分组/代理文件，并遍历 2 万条 recent ring 查最近状态。迁移后先分页获取账号，再批量查询关系与摘要；不得逐账号发数条 SQL。关系 JOIN 导致重复行时先聚合关系或分两次查询，不在重复行上直接 LIMIT。
- **列表不读取凭据和长错误正文。** 只选展示字段，详情另取；账号数、page_size、时间范围、导入行数均设明确上限。当前 overview 的 from/to 没有硬范围上限，不应允许异常跨度触发超大点数组。
- **总数与详情分开。** 最近日志使用 has_more；确有总数需求时单独查询/缓存。大范围日志不能每翻一页都执行全表 COUNT 和大 OFFSET。
- **聚合预计算。** 仪表盘查询 minute/day 聚合，最近错误查询明细。写入唯一 event_id，聚合更新与事件消费保持幂等，重启后可从持久检查点补齐，不能只依赖内存计数器。
- **明确时区与指标口径。** 时间存 timestamptz；“今日”按配置时区计算；同一时间范围在卡片、趋势、账号榜单和日志中一致。分母为零显示“暂无样本”，不要伪造 0% 健康状态。
- **控制保留期。** 先按体量选择普通表与定期小批清理；明细达到较大规模且清理昂贵时再按月分区，聚合保留更久。时间分区表的唯一约束需要包含分区键，event_id 去重设计要同步调整。见 [PostgreSQL 分区文档](https://www.postgresql.org/docs/current/ddl-partitioning.html)。
- **连接池有界。** 应用连接上限根据主节点已有业务余量设定，设置连接获取超时、statement_timeout 与锁等待上限；PG、Redis 用独立账号/命名空间。不要照搬服务器总连接数给单个应用。
- **通过测量验收。** 接入 pg_stat_statements，关注总耗时、调用数、读取行数和临时排序；用代表性数据执行 EXPLAIN (ANALYZE, BUFFERS)。先有执行计划再确定索引，不能把“用了 Redis”当成性能优化已经完成。参考 [pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html)、[EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)。

Redis 初期只缓存确有重复访问的概览，建议从 5–15 秒 TTL 起步；账号静态选项可短期缓存并在修改后失效。增加超时与连接池上限，缓存故障可回源 PG；管理会话验证故障应返回明确不可用，不得绕过认证。不要长期缓存完整账号凭据列表。

前端构建实际输出两个约 1.13 MB、1.21 MB 的 JS chunk（gzip 合计约 768 KB），CSS 约 382 KB。当前 Element Plus、全部图标、ECharts 都是整库导入。建议按组件/图标导入，ECharts 只注册 Line/Bar/Pie/Scatter、Tooltip/Grid/Legend 等实际模块；保留页面懒加载。拆 chunk 只改变加载边界，不能替代实际减少依赖。

## 6. 推荐实施顺序与验收

1. **先修正确性**：导入覆盖、JSON 误解析、tooltip HTML、密钥轮换原子性、退出最终保存、比例单位、日志顺序。保留现有页面风格，避免同时大改交互。
2. **迁移 PG + Redis**：建 schema/migrations → 导入工具 dry-run → 单独环境校验数量/身份/关联/过期时间 → 短暂停写切换 → 校验 → 保留明确回退路径。令牌轮换不能由旧、新两套进程同时运行。迁移过程中不得将令牌写进报告或普通日志。
3. **补使用体验**：响应式布局、分页搜索、详情抽屉、导入预览、批量管理、真实通知、审计。
4. **基于数据优化**：加入规模测试、SQL 执行计划、前端包体和页面响应指标，再决定缓存与分区。

验收至少包括：两条不同 JWT 不互相覆盖；多行 JSON 可正确导入；删除关系故障不返回假成功；正常退出和重启后日志/聚合一致；账号状态不因重启变正常；缓存率 0.8 显示 80%；320/390/768/1440px 下主要操作可达；四种主题文本和错误可读；所有列表均有明确分页/查询范围；Redis 停机时缓存回源且会话认证不放行。
