# 2026-09-27 App Server 502 与用量修复

## 观测与原因

上海时间 14:00 起抓取的 66 条记录均走 `official_app_server`：60 条成功、6 条 502。成功记录中，51 条流式响应全部缺少用量，9 条 JSON 响应已记录用量。

- 502：历史 custom 工具被错误要求仍在本轮工具目录；解除该限制后，真实 CLI 跨模型恢复又暴露 `fc_` item ID 与原生 custom 类型不符，官方返回 `invalid_id_prefix`。只修正重放边界的类型前缀，即可恢复同一段历史。
- 用量：流式分支只观察进度与首输出，未调用普通 JSON 分支的终态计量。因此缺失的是记录，并不能据此判断没有上游缓存。
- 模型：列表在返回模型等于请求模型时隐藏了字段；适配器也需要区分官方线程确认值与请求值，不能用请求值伪造返回来源。
- 延迟：旧批次成功请求的首输出中位数为 5.522 秒、P95 为 14.180 秒。每个新线程重复取官方模型目录约占 0.455–0.522 秒，不能独自解释全部等待；推理摘要曾等完整项结束才转发，也推迟了首输出。

## 修复

1. 允许不再声明的历史工具作为历史项重放；按原生类型转换 `fc_/ctc_` 与 `fco_/ctco_` 前缀，保留 `call_id`、后缀和对外流式 ID。本轮可执行工具仍按当前声明验证。
2. SSE、JSON、工具暂停及续接、压缩响应统一读取真实终态 usage。缺少数据保持未知，实测零保留零；生成完成后的本地持久化失败仍保留已发生的上游用量。
3. 返回模型取官方 thread/settings/rerouted 确认值，保留来源；列表始终展示已记录的返回模型。
4. 即时转发真实推理摘要；新增 `official_runtime_ms`、`official_inference_ms` 阶段供日志详情和导出检查。模型目录按账号、凭据、代理隔离短缓存，避免重复 bootstrap。

## 发布前发现的内存限制

生产服务在上海时间 14:18 和 15:01 两次因内存限制重启。内核日志明确记录 `CONSTRAINT_MEMCG`，触发范围为 `codex-agent.service`，被终止进程为官方 `codex`；服务配置为 `MemoryMax=2147483648`（2 GiB）、`OOMPolicy=stop`，并非仅凭 PID 变化推断重启原因。

15:01:24 启动的进程为 PID 1698380。通过主机路径与 `/proc/1698380/root` 分别核查，实际 `CODEX_RUNTIME_DIR` 均映射到 `/var/lib/private/codex-agent/official-runtime`，共有 58 个会话目录、45 份 rollout，最新文件时间仍为 14:18:07。新增 15 条缺失记录没有可匹配的官方 `token_usage_record`，独立恢复计划匹配数为零，未执行空修复。

内核事件对应 53–56 个官方 Codex 进程；主机总内存约 125 GiB、可用约 94.75 GiB，明确为服务自己的 2 GiB cgroup 限额触发。根据用户最后指令，MemoryMax、MemoryHigh、MemorySwapMax、TasksMax 已持久设为 infinity，cgroup 四项均为 max，变更即时生效且没有重启服务。

同时移除官方运行时 64 进程、128 任务和 64 次并发目录获取的拒绝门槛、任务 30 分钟总截止、活会话 1 小时闲置清理及完成任务 24 小时清理；移除官方内部消息、累计事件、任务文件和原生 RPC WebSocket 的人工大小上限。已退出进程仍正常回收，取消和授权校验仍生效。透明目录缓存淘汰以及 HTTP 协议校验并不是会话容量配额，维持现有处理；上游模型上下文/账号额度也不是网关可取消的限制。

用户明确要求保留账号并发：两个账号维持各 50，账号逻辑和配置未修改。

## 0.4.3 工具发现补充

生产压力请求进一步暴露默认工具命名空间及发现流程边界：

- 官方协议把顶层工具的省略 namespace 与 `functions` 视为同义。网关现在只对已声明的顶层工具接受这两个等价形式，不接受其它命名空间、未声明名称或跨域别名。未修改的官方 App Server 配合本地协议模型明确复现：raw item 保留 `functions`，随后官方 RPC 正常派发为省略 namespace；原桥接会错误拒绝。
- client-owned `tool_search` 通过函数包装重放，`tsc_` 与 `fc_` item ID 按实际类型双向转换，保留不变的 `call_id`。真实三阶段验证涵盖搜索请求、客户端发现新工具、实际工具调用及结果回传，各阶段用量完整。
- 客户端只声明 deferred 工具、未声明 `tool_search` 时，官方运行时会自动执行工具发现。网关现在允许这种隐式 server-owned 发现并严格核对返回工具定义；显式 client-owned 发现仍由客户端执行。
- 发现后同一个工具的 `defer_loading` 从 true 变成省略/false 时，合并为已激活工具；其他 schema、类型和描述差异仍校验。显式发现和隐式发现均已完成三段真实请求验证，包含发现后的再次续聊。
- 请求账号官方目录不存在的模型返回 HTTP 400，保留所请求模型，不再把不支持的模型配置归为 HTTP 502，也不自动替换模型。

部分旧 `undeclared tool` 错误的运行时工作区已在失败关闭时删除，无法逐条取得其原始工具标识；不能声称全部旧错误拥有同一根因。新增错误诊断保留受控的 namespace/name/声明数量，不包含参数、提示词或凭据。

## 会话存储与错误分类完整性

全量失败分类还发现会话存储失败及未记录原因的 HTTP 409/503。Redis 配置仍是 maxmemory 128 MiB、noeviction，而历史缓存接近 114 MiB，另有 Redis 自身内存开销。服务健康 PING 可成功但不能证明写入正常；运行用户禁止 INFO/CONFIG，因此没有读取 OOM errorstats，不把容量关联冒充取得了原始 Redis 错误。

已只针对本项目 Redis 解除 maxmemory、容器 CPU/内存/进程限额，保留 AOF 数据卷、密码、ACL 和 noeviction。变更后的 160 秒真实业务有 252 次请求，其中 217 成功；conversation/session storage 错误、HTTP 409、HTTP 503 均为零。旧 409 没有错误正文，无法逐条恢复它们的准确原因。

官方模式的历史缓存已与 PowerPoint 的有界缓存分离：官方记录永久保存，不再由 1 小时 TTL、512 条或 128 MiB 预算淘汰；原生官方 HTTP/WS 入站及回传不再套用兼容通道的 32 MiB / 64 流限制。原始模式、客户端 key、会话和账号归属检查保留。待迁移的存留官方记录只修改 expiry 为零，校验其余内容不变并通过 Redis compare-and-set 防止覆盖并发新值。

错误日志在授权与读取请求阶段即开始观察，补齐早期错误原因和来源；只捕获有界的实际错误响应，不将正常生成文本误作错误。客户端主动取消记录为 aborted/client，不再伪装为 502；官方 JSON-RPC 的结构化错误保留受控 code/message。模型不支持、无效 schema 和上下文超限按实际 4xx 返回，额度/速率限制按 429 返回，不静默替换模型或篡改请求。

`gpt-5.4` 使用未修改的官方 App Server 实测明确被上游拒绝用于 ChatGPT 账号；这类输入不能通过网关制造可用模型。已失去原文的旧错误和原始用量不凭猜测重写。
