## 实际干预及证据缺口

运行源端已是 profile 连续性修复版本 `74c42b0e…`，所以前组是“修复已部署、仍使用旧 AT”；不是旧代码与新代码的直接随机对照。固定网关为 `a52ad225…`，原生 helper 为 `9110b869…`，CLI 为 `660e159a…`。

28765 没有公开的指定子号强制重新授权 API，正常协调流程会优先验证、复用旧 token。因此实验通过现有内部授权、租约、身份验证、保存和正常推送函数，各账号调用一次授权入口。没有伪造401、删除凭据或修改画像来强迫重登。“入口一次”不代表内部所有 HTTP 步骤只有一次。

第一次预检因包含未被子号流程使用的母号画像而停止，实际零租约、零授权、零推送。后续仅将未消费画像改为观测项，保留身份、实际路由、分配、子号画像和凭据门禁；以新 action 保存记录，原停止回执不改。

new2 的授权入口调用后，主控缺失后续回执。只读观察确认源端及网关都已更新 AT、独立 DID/profile 与新 AT 绑定、浏览器凭据组未变，源端显示成功且有推送成功事件，相关 worker 与租约已不存在。但没有本次 OAuth 返回原始摘要和完整过程回执，无法补造“该动作全流程受控完成”的证据。

源码与合成测试另外证实工具缺陷：授权流程会直接向 stdout 输出普通文本，而旧工具把每一行当 JSON 回执。`logging.disable` 无法抑制这些输出，解析失败会提前丢失子进程后续记录。这能复现现场同形症状；因为没有保存现场触发行和异常类别，未认定它是本次唯一确切原因。

工具已改为独立带帧格式的收据通道，屏蔽应用 stdout/stderr，checkpoint 先原子落盘再发送；解析失败仍读取并回收子进程。Windows 与生产同镜像 Linux 的9项真实子进程测试均通过。随后只执行尚未调用过的 new1，未重复授权 new2：new1 完成一次授权、一次正常推送，收到7帧、无协议错误；容器中9份持久文件与主控记录匹配，授权返回 AT/RT/DID/profile、源端存储和网关读回一致，租约释放。
